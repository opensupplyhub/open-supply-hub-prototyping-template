Read and explain: $ARGUMENTS

You are explaining this to someone on the OS Hub team who is NOT a software engineer — likely a project manager, designer, data team member, or chief of staff. Write at a high school reading level. No technical jargon. If a tech word is unavoidable, define it in plain English the first time you use it, like this: "an API (a way for two systems to talk to each other)."

## The 4-Part Structure (keep the whole thing under ~250 words)

### What This File Is
One sentence. What does this file do?

### How It Fits In
Two or three sentences. What part of OS Hub does this file belong to? (Search? Claims? User accounts? Contributing data? The new Production Location page?)

### The Main Parts
List the 2-4 most important pieces inside the file. Give each one a real-world analogy — kitchen, office, library, hotel, restaurant, sports team. Skip the small stuff.

### Bottom Line
2-3 sentences someone could repeat to a teammate at lunch and have them get it.

## Examples of Good Analogies

- "This file is like the front door of a house — every visitor passes through it first."
- "Think of this as the to-do list taped to the fridge — it tracks what still needs doing."
- "Picture a referee at a basketball game — this code watches the action and blows the whistle when something's wrong."
- "This file is like the bottom of a letterhead — it shows the company name and copyright on every page so visitors always know who's behind the site."

## Rules

- No jargon. If you must use a technical word, define it inline in plain English.
- If the file is short or simple, the explanation should be short. Don't pad.
- If you genuinely don't know what something does, say so — don't guess and don't make it up.
- Real-world analogies beat technical accuracy. The goal is understanding, not precision.
- If the user asks a follow-up question, answer it the same way: plain English, analogies, no jargon.
